# 1.0 release audit

October 17, 2026. Target: 1.0.0, build 9, Apple Silicon. The maintainer explicitly chose to retain the existing local signing identity rather than wait for Developer ID and notarization. This is a stable release, not a GitHub prerelease. The preceding 0.1.5 build 8 candidate was not published.

## Scope and fixes

Three independent code reviews covered the current source, advertised behavior, failure handling, lifecycle, settings and distribution. The shipping source/resource scan found no TODOs, dummy URLs, lorem ipsum, coming-soon controls or unimplemented feature buttons. Development-only updater messages and preview sample data are intentional; the release embeds the live feed and verification key.

| Finding | Result | Evidence and limits |
| --- | --- | --- |
| Caps Lock could not interrupt persistent offline | Caps Lock uses its configured temporary duration and offline restores afterward; a lower timer stays put | 99-test core suite and signed-app routing check |
| Menu action could affect a different timer after selection changed | Menu items retain their displayed Clock reading; dispatch checks the identifier and the expected pause state | Isolated Clock-menu harness runs the production matcher with changed IDs/states |
| Compact Clock control did nothing with a mirror but no Clock process | One background open request, with bounded retries tied to the user request rather than observer reconnection | Injected opener fixture; actual launch-to-control timing remains unverified |
| Delayed status menu could appear after another interaction | Outside mouse/key input or another app's activation cancels the pending request; monitors are removed on completion/cancellation | Source/lifecycle review and release compilation; live interaction unverified because app control timed out |
| Repeated brightness target could be skipped after an external adjustment | A new adjustment clears the stale hardware-write cache; ramp-step duplicate writes remain skipped | Actual controller with fake I2C: failed before the fix, passed afterward for fresh/cached baselines and combined MonitorControl scale |
| Consumed media keys could disappear during stop/pause | Deferred events are replayed on stop or a cancelled handoff using the existing replay tagging | Real event-admission callback with captured replay, without posting events to macOS |
| Late callbacks could restore alerts after sleep | Temporary presentation and persistent Caps Lock are gated while sleeping | Source trace and compilation; hardware sleep timing not reproduced |
| Multiple finished timers could merge indistinguishable action pairs | One Clock banner supplies the custom card; additional banners retain native controls. The selected banner is preferred on later scans | Source invariant: only one matched banner can contribute actions/duration. Two simultaneous real completions remain a manual check |
| Display preference implied all persistent activities followed it | Label now says “Show brief alerts on,” matching existing routing | Source review; persistent placement policy unchanged |

## Verification run

- 99 Swift tests in 30 suites and six Python update-configuration tests passed.
- Native lifecycle checks passed for AirDrop, microphone, output, media keys, external brightness, diagnostic, internet, settings persistence and Clock menu actions.
- The final signed app passed routing, persistence, promotion, expanded-card motion and input checks. These instantiate real panels without changing user hardware/timers.
- Network stress passed 16,000 sessions and 160,000 path events, with no leftover deadlines. Real loopback probes retained the 30-second cadence. Over 93 seconds, the probe harness used about 0.007% of one CPU core and stayed near 3.1 MiB. This is a bounded probe test, not whole-app battery-life measurement.
- Native app control timed out even after the user opened Settings. No current screenshots were accepted, and no completed visual-flow or accessibility audit is claimed. A stack sample showed an operating main event loop, not evidence of a hung main thread.
- The updater implementation is unchanged from the earlier cancellation/install/relaunch test documented in verification.md. An interactive upgrade to this exact release was not rerun. The maintainer reports that another person installed the app successfully; the recipient's OS/model and full permission/update workflow are not recorded.

## Attention and maintainer input

1. **Signing, decided:** publish with the current local signature. First launch may require the documented Open Anyway step. Developer ID/notarization remains optional future distribution work.
2. **Compatibility testing:** macOS 14 is the deployment floor; runtime checks here use macOS 27. A recipient has confirmed installation on another Mac. Its OS/model and complete permission/update checks are unknown; older macOS and additional monitor/AirPods models still need coverage. Intel is outside the declared release scope.
3. **Clock coverage:** non-English controls, simultaneous finished timers and actual launch-to-control timing need manual validation. Unsupported native interfaces keep their native fallback where available.
4. **Native popups and visual checks:** a first-frame native popup can still flash, including on secondary displays. The Settings visual audit remains unverified because the control tool could not attach. No zero-flash or full accessibility-compliance claim is made.
5. **Declared feature limits:** AirDrop acceptance/progress and call-app-specific mute are outside this release. Internet state is based on the configured IPv4 ICMP target; blocked ping replies can report offline. These are documented boundaries, not placeholder implementations.

No further product decision is needed to publish the existing declared scope. Expanding OS/device support, languages, AirDrop transfer controls or notarization requires the relevant hardware, access or a separate feature decision.
